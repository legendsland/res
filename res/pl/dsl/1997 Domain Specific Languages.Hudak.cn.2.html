1　引言1 Introduction

大多数人想到编程语言时，想到的是通用语言：它能够以大体相同的表达能力和效率，为任何应用编写程序。然而，对许多应用而言，表达问题解决方案的方式，可以比通用编程语言提供的方式更加自然。因此，近年来研究人员与实践者开发了许多不同的领域特定语言（DSL），专门面向特定应用领域。使用恰当的 DSL，可以比使用通用语言更快、更有效地开发该领域的完整应用程序。理想情况下，设计良好的 DSL 应当精确捕获应用领域的语义，不多也不少。When most people think of a programming language they think of a general purpose language: one capable of programming any application with relatively the same degree of expressiveness and efficiency. For many applications, however, there are more natural ways to express the solution to a problem than those afforded by general purpose programming languages. As a result, researchers and practitioners in recent years have developed many different domain specific languages, or DSL’s, which are tailored to particular application domains. With an appropriate DSL, one can develop complete application programs for a domain more quickly and more effectively than with a general purpose language. Ideally, a well-designed DSL captures precisely the semantics of an application domain, no more and no less.

从另一个角度看 DSL，人们常说，抽象是编写好软件最重要的因素，我对此深信不疑。软件设计者接受训练，学习使用各种抽象机制：抽象数据类型、（高阶）函数与过程、模块、类、对象、单子、续延等。这些机制的一个重要特点是相当通用；例如，大多数算法策略和计算结构，既可以用函数式抽象技术实现，也可以用面向对象抽象技术实现。通用性固然好，但我们仍可以追问：对某个特定应用而言，理想的抽象是什么？在我看来，它就是 DSL——问题领域的“终极抽象”。For another perspective of DSLs, it is often said that abstraction is the most important factor in writing good software, a point which I firmly believe in. Software designers are trained to use a variety of abstraction mechanisms: abstract data-types, (higher-order) functions and procedures, modules, classes, objects, monads, continuations, etc. An important point about these mechanisms is that they are fairly general—for example, most algorithmic strategies and computational structures can be implemented using either functional or object-oriented abstraction techniques. Although generality is good, we might ask what the ideal abstraction for a particular application is. In my opinion it is a DSL: the “ultimate abstraction” of a problem domain.

优点　与使用较传统语言编写的程序相比，DSL 程序具有以下优点：Advantages Programs written in a DSL have the following advantages over those written in more conventional languages:

  • 更加简洁they are more concise
  • 编写速度更快they can be written more quickly
  • 更容易维护they are easier to maintain
  • 更容易推理they are easier to reason about

这些优点，与人们宣称传统高级语言程序具有的优点相同。因此，DSL 是否只不过是层次更高的高级语言？These advantages are the same as those claimed for progams written in conventional high-level languages, so perhaps DSL’s are just very high-level languages?

某种意义上确实如此。但 DSL 程序还有另一个重要特点：In some sense this is true. But programs written in a DSL also have one other important characteristic:

  • 往往可以由非程序员编写they can often be written by non-programmers

更准确地说，它们可以由不懂编程、但精通 DSL 所面向领域的人编写。这有助于弥合开发者与用户之间的鸿沟——有时甚至是深渊；它可能构成软件开发中巨大的隐性成本。这也揭示了 DSL 设计的一个重要事实：沉浸于某个领域的用户，本来就理解该领域的语义。DSL 设计者只需提供一种表达这些语义的记法。More precisely, they can be written by non-programmers who are nevertheless experts in the domain for which the DSL was designed. This helps bridge the gap (often a chasm) between developer and user, a potentially major hidden cost in software development. It also raises an important point about DSL design: a user immersed in a domain already knows the domain semantics. All the DSL designer needs to do is provide a notation to express that semantics.

再看一个例子。假设我们正在实现一门编程语言，其 BNF 语法包含以下规约 [ASU87]：As another example, suppose we are implementing a programming language whose BNF syntax includes the following specification [ASU87]:

expr   = expr + term | term
term   = term ∗ factor | factor
factor = (expr) | digit

这是定义简单算术表达式的标准方法。使用 Yacc [Joh75]，几乎可以直接采用这份规约：which is the standard way to define simple arithmetic expressions. Using Yacc [Joh75], this specification can be used almost directly:

expr    : expr '+' term
        | term            ;
term    : term '*' factor
        | factor          ;
factor  : '(' expr ')'
        | DIGIT           ;

Yacc 接收这段代码，并为其表示的小语言生成语法分析器；换言之，Yacc 是一个生成其他程序的程序。它还有一些功能，可以指定代码各行对应的动作。我同样认为，如果你熟悉 BNF 语法和基本 C 编程，一天之内就能教会你熟练使用 Yacc。Yacc will take this code and generate a parser for the little language that it represents; i.e. Yacc is a program that generates other programs. It also has several other features which allow one to specify actions to be taken for each line in the code. I also believe that, if you are familiar with BNF syntax and basic C programming, I could teach you how to use Yacc expertly within one day’s time.

最后看一些 SQL 代码。SQL 用于创建和查询关系数据库。这里略过建立数据库的方式，重点看查询的样子。第一个例子如下：As a final example, let’s look at some SQL code. SQL is a language for creating and querying relational databases. We will ignore how SQL is used to set up a database, and concentrate on what queries look like. Here is the first example:

SELECT  firstName, lastName, address
FROM    employee
WHERE   firstName = 'Cathy' AND birthDate = '07/04/1950'

这个查询几乎不言自明：从 employee 关系中选出员工的名、姓和地址，条件是名字为 Cathy，且出生日期为 1950 年 7 月 4 日。SQL 查询可以相当复杂，例如可以像下面这样嵌套：This query is almost self-explanatory: it is SELECTing the first name, last name, and address FROM the employee relation WHERE the first name of the employee is Cathy AND she was born on July 4, 1950. SQL queries can be quite complex; for example they can be nested, as in the following:

SELECT firstName, lastName, address
FROM   employee
WHERE  salary > ALL (SELECT salary
                     FROM employee
                     WHERE firstName = 'Paul')

该查询选出工资高于每一位名叫 Paul 的员工的所有员工。This query selects all employees whose salary is greater than that of any employee whose first name is Paul.

SQL 是强大的数据库编程语言，当然，也有 QUEL 等其他语言被认为更强大。如果你熟悉数据库，我觉得一天之内就能学到不少 SQL；但要在真实数据库系统中成为熟练使用这一 DSL 的专家，可能需要多年。SQL is a powerful language for programming databases (there are other languages that are claimed to be more powerful, such as QUEL). If you are familiar with databases, my feeling is that you could learn quite a bit about SQL within a day’s time, although it might take years to become an expert at using this particular DSL in the context of real-world database systems.

本文余下部分将讨论 DSL 的动机、基本特征、设计与实现方式、如何嵌入现有语言，以及未来发展方向。我尤其希望传达这样一个观点：你完全可以“自己动手”创建 DSL，不必依赖现成 DSL，也能利用这一有益技术。3In the remainder of this article I will discuss the motivation of DSL’s, their basic characteristics, how to design and implement them, how to embed them in existing languages, and avenues for further development. I am particulary keen on conveying the idea that you can “roll your own” DSL: you don’t have to rely on existing DSL’s to take advantage of this useful technology.3

2　DSL 软件开发方法2 The DSL Software Development Method

基本的“DSL 软件开发方法”可以概括如下：The basic “DSL Software Development Method” can be summarized as follows:

  1. 1. 确定你的领域。1. Define your domain.
  2. 2. 设计能够准确捕获领域语义的 DSL。2. Design a DSL that accurately captures the domain semantics.
  3. 3. 构建支持 DSL 的软件工具。3. Build sofware tools to support the DSL.
  4. 4. 利用新的 DSL 基础设施开发应用程序，即领域实例。4. Develop applications (domain instances) using the new DSL infrastructure.

当然，这不一定是线性过程；修改、细化、增强等往往不可或缺。Of course, this is not necessarily a linear process: revision, refinement, enhancement, etc. are often necessary.

前两步很困难，却是成功应用这一方法的关键。如果领域本身界定得当，DSL 设计应当比较顺利，尤其当你已经具备基本编程语言原理方面的经验时。The first two steps are difficult, but are the key to successful application of the methodology. If the domain itself is properly identified, the DSL design should go smoothly, especially if you have experience in basic programming language principles to begin with.

实现 DSL 有多种方式。如果将它看作传统语言，就可以使用传统技术：根据 BNF 语法构建常规词法分析器和语法分析器；对语法分析器生成的抽象语法进行各种高层分析、变换和优化；最后为某种宿主机器生成可执行代码。针对 DSL，这种标准方法可以作如下调整：There are several ways in which one could implement a DSL. If treated as a conventional language, conventional techniques could be used: build a conventional lexer and parser based on the BNF syntax; perform various high-level analyses, transformations, and optimizations on the abstract syntax generated by the parser; and then generate executable code for some host machine. In the case of a DSL, this standard approach may be modifed in a number of ways:

  1. 1. 使用 Lex、Yacc——它们本身也是 DSL——或类似工具，简化词法分析器与语法分析器的构建。1. Use Lex and Yacc (themselves DSL’s), or similar tools, to facilitate the construction of the lexer and parser.
  2. 2. 使用结构化编辑器或其他编程环境生成器，例如 Synthesizer Generator [Rep84]，为更复杂的编程环境建立基础设施。2. Use a structured editor or other programming environment generator (such as the Synthesizer Generator [Rep84]) to create the infrastructure for a more sophisticated programming environment.
  3. 3. 为抽象机（例如字节码解释器）而不是真实机器生成代码，或者生成 C 等另一门语言的代码。3. Generate code for an abstract machine (e.g. a byte-code interpreter) rather a real machine, or generate code in another language, such as C.
  4. 4. 编写解释器，而不是编译器。4. Write an interpreter rather than a compiler.

下一节讨论另一种 DSL 实现方式。Another way to implement DSL’s is discussed in the next section.

3　领域特定嵌入式语言3 Domain Specific Embedded Languages

尽管前景诱人，DSL 方法仍有潜在问题。首先，性能可能不佳：层次很高的语言往往不如低层语言高效。如果传统语言的性能已经成问题，设计 DSL 未必是最佳方案。另一方面，在某些领域，可以对 DSL 程序作高层优化，而优化结果足够复杂，直接用传统语言编写会困难、繁琐且容易出错。数据库查询优化就是一个例子；在这种情形下，可以将 DSL 视为提高性能的手段。无论如何，许多应用领域的瓶颈并非性能，因此这一顾虑并不足以否定 DSL。Despite all of the promise, there are potential problems with the DSL methodology. To start, it may be that performance is poor: very high-level languages are notoriously less efficient than lower-level languages. If performance using conventional languages is already a problem, designing a DSL may not be the best approach. On the other hand, there are certain domains where high-level optimizations are possible on DSL programs, whose results are sufficienty complex that programming them directly in a conventional language is difficult, tedious, and error-prone. Query optimizations in the domain of databases is an example of this, and in such cases a DSL may be justified as a way to improve performance. In any case, there are many application domains where performance is not the bottleneck, so this argument is not a show-stopper.

另一个顾虑是，每个领域都创建一种新语言，会产生一座“巴别塔”。这当然值得担心。不过，如果语言足够简单，问题可能并没有想象中严重。后面还将讨论，如何让新 DSL 在外观与使用方式上足够相似，从而降低学习多种新语言的负担。Another concern is the generation of a “Tower of Babel” through the creation of a new language for every domain. This is certainly a valid concern. On the other hand, if the languages are simple enough, the problem might not be nearly as bad as one might think, and in a later section we will discuss ways to make new DSL’s similar enough in look-and-feel to reduce the overhead of learning many new languages.

最后一个顾虑，是可能难以承受的启动成本：设计时间、实现、文档等。从零设计并实现编程语言，可能相当困难；投入两到五年并不少见。而且，我们很可能第一次并不能做好。DSL 会演进，我们也将经历随之而来的各种困难。具体地说，如果图 1 中的启动成本高得让我们永远无法收支平衡，该怎么办？如果设计完全错了，在软件系统的生命周期中，还要反复承担几次启动成本，又怎么办？A final concern is the potential for unacceptable start-up costs: design time, implementation, documentation, etc. It can be fairly difficult to design and implement a programming language from scratch: a 2-5 year effort is not uncommon. Moreover, there’s a good chance that we won’t get it right the first time. The DSL will evolve, and we will experience all of the difficulties associated with that evolution. To state this concern in concrete terms, what if the start-up costs shown in Figure 1 are so high that we never break even? Or what if we get it all wrong, and incur the start-up cost several more times during a software system’s life-cycle?

每种软件设计方法都潜藏危险，当然也不存在银弹。无论采用什么方法，都必须理解其收益与局限，谨慎前行。There are dangers lurking in every software design methodology, and there are no silver bullets, of course. We must understand the benefits as well as the limitations of whatever methodology we are using, and proceed with caution.

对于 DSL 方法，我想用本文剩余篇幅讨论几种技术，它们可以大幅缓解上述大多数问题。这些技术建立在两个关键想法之上：In the case of the DSL methodology, I would like to use the rest of this article to discuss several techniques that can greatly alleviate most of the problems addressed above. These techniques rest on two key thoughts:

  • 首先假定，我们其实并不想从零构建新的编程语言。更好的办法是继承另一门语言的基础设施，再针对目标领域作专门定制，得到领域特定嵌入式语言（DSEL）。We begin with the assumption that we really don’t want to build a new programming language from scratch. Better, let’s inherit the infrastructure of some other language—tailoring it in special ways to the domain of interest—thus yielding a domain-specific embedded language (DSEL).
  • 在此基础上，就可以集中精力处理语义问题，利用良好的抽象原则构建语言工具，使工具本身易于理解、高度模块化，并且容易演进。Building on this base, we can then concentrate on semantical issues. Sound abstraction principles can be used at this level to build language tools that are themselves easy to understand, highly modular, and straightforward to evolve.

以下各节将进一步阐述这些想法。In the following sections I will elaborate on these ideas.

3.1　语法与语义3.1 Syntax vs. Semantics

Lex [Les75]、Yacc [Joh75]，以及更复杂的编程环境生成器（例如 [Rep84]），已经证明对设计新编程语言很有用，当然比从零编写词法分析器和语法分析器更好。但使用它们依然相当繁琐；而且，无论如何，语法细枝末节理应是语言设计者最不需要担心的事情。这也是编程语言圈里常高喊的“语义比语法更重要”口号的另一种说法。这并不是说语法不重要——我认为它重要——而是要恰当地看待语法。Tools such as Lex [Les75] and Yacc [Joh75], as well as more sophisticated programming environment generators (e.g. [Rep84]), have been shown to be quite useful in designing new programming languages; they are certainly better than building lexers and parsers from scratch. On the other hand, they are still rather tedious to use, and in any case syntactic minutiae should arguably be the least of a language designer’s worries. This is another twist on the slogan “semantics is more important than syntax” often bellowed in programming language circles. This is not to say that syntax doesn’t matter—I believe that it does—but rather places syntax in proper perspective.

然而，即使聚焦语义，许多细节仍然并不那么重要。即便是参数求值顺序这样的深层问题，只要清楚所用语言的确切规则，人们通常也能适应。变量绑定构造的精确行为、模式匹配规则、类型系统中无穷无尽的细节、模块功能的重大差异等，都是编程语言设计界激烈争论的例子。其他语义细节还包括预定义函数的名称、参数在书写上的次序、它们在各种情况下的确切行为，以及让编程语言能够实际使用的软件库功能所涉及的无尽类似问题。However, when one focuses on semantical issues, many of the details still don’t matter much. Even a deep issue such as the evaluation order of arguments is often something that people can adjust to, as long as they know exactly what it is for the language they are using. The precise behavior of variable-binding constructs, pattern-matching rules, endless details in type systems, major differences in module functionality, etc. are examples of debates that rage in the programming language design community. Other examples of semantical minutiae include names of pre-defined functions, the lexical order of their arguments, exactly how they behave under all circumstances, and an endless list of similar issues concerning the functionality of the software libraries that are essential to making a programming language practical.

归根结底，一旦选定编程语言，人们就会把工作完成，而且通常很欣赏自己使用的高级语言。The bottom line is that, once a programming language is chosen, people get the job done, and they usually well appreciate the high-level language that they are using.

3.2　DSEL 继承语言特性3.2 DSELs Inherit Language Features

关键在于：与其从零设计编程语言，为什么不借用另一门语言已经作出的大多数设计决策？既然如此，也尽量借用为那门语言设计的工具。除了复用大量思想与成果这一明显优点，DSEL 相对于 DSL 还有一些优势：The point is, instead of designing a programming language from scratch, why not borrow most of the design decisions made for some other language? And while we’re at it, let’s borrow as many as we can of the tools designed for this other language as well. Aside from the obvious advantage of being able to reuse many ideas and artifacts, DSELs have certain advantage over DSLs:

首先，虽然前面说 DSL“应当精确捕获应用领域的语义，不多也不少”，但事实上，DSL 通常并非完全孤立地使用。即便是——甚至尤其是——最优雅的 DSL，其用户也可能因为无法使用更通用的编程语言特性而感到受限。First off, although I pointed out earlier that a DSL “should capture precisely the semantics of an application domain, no more and no less,” a DSL in fact is not usually used in total isolation. Users of even (or perhaps especially) the most elegant DSLs may find themselves frustrated at not having access to more general programming language features.

其次，如果为不同领域设计的多种 DSEL 都源自同一基础语言，不同领域的程序员就能共享一门核心语言。大型应用很可能包含不止一种 DSEL；让它们具有相似的外观与使用方式，显然很有好处。Secondly, if we design several DSELs for different domains, all derived from the same base language, then programmers in the different domains can share a common core language. Indeed, for a large application it is quite conceivable to have more than one DSEL. For them all to have a similar look-and-feel is a clear advantage.

总之，DSEL 方法建立了丰富的基础设施，能够：In summary, the DSEL approach creates a rich infrastructure that:

  1. 1. 支持快速设计 DSL；至少可以把它视为一种构建 DSL 原型的方式。1. Allows for rapid DSL design; if nothing else, it can be viewed as a way to prototype a DSL.
  2. 2. 便于变更，无论是为了试验、纠错，还是设计演进。2. Facilitates change, whether for experimentation, fault correction, or design evolution.
  3. 3. 提供熟悉的外观与使用方式，尤其当多种 DSL 嵌入同一语言时。换言之，缩小了巴别塔的规模。3. Provides a familiar look and feel, especially for several different DSL’s embedded in the same language. In other words, it reduces the size of the Tower of Babel.
  4. 4. 便于复用语法、语义、实现代码、软件工具、文档及其他相关成果。4. Facilitates reuse of syntax, semantics, implementation code, software tools, documentation, and other related artifacts.

当然，这种方法也潜藏危险：DSL 可能受到底层“宿主”语言的能力与偏向限制。重要的是，先从抽象层面设计 DSL，再寻找合适的宿主。Of course, there is danger lurking in this approach as well: we may find that our DSL becomes limited by the power and prejudices of the underlying “host” language. It is important to design the DSL abstractly first, and then search for a suitable host.

实现 DSEL，可以为宿主语言编写预处理器，必要时再为程序输出编写后处理器；也可以直接修改宿主语言的实现。前者更可取，因为它避免依赖其他不断演进的系统。在许多情况下，甚至完全不需要预处理器就能实现嵌入；为此，宿主语言必须拥有足够丰富的语法与语义，稍后会看到实例。Implementing a DSEL can be achieved by writing a pre-processor for the host language (and possibly a post-processor of program output), or by directly modifying the host language implementation. The former is more desirable since it removes dependency on other evolving systems. In many cases the embedding can be achieved without any pre-processor at all: for this to work, the host language needs to be suitably rich in syntax and semantics (we will see examples of this shortly).

本文余下部分将介绍使用函数式语言 Haskell [HPJWe92] 构建 DSEL 的成果。Haskell 的一些特性，尤其是高阶函数、惰性求值和类型类，使它特别适合这项工作；但也完全可以考虑使用其他语言。另一方面，据我所知，还有一些能进一步简化这项工作的特性，目前任何语言都不具备。因此，仍有许多工作要做。In the remainder of this article I will describe the results of using the functional language Haskell [HPJWe92] to build DSELs. Haskell has several features that make it particularly suitable for this—in particular, higher-order functions, lazy evaluation, and type classes—but other languages could conceivably be used instead. On the other hand, there are features that don’t exist in any language (to my knowledge) that would make things even easier; there is much more work to be done.

可以将它读作：“r1 与 r2 的交集是一个区域；将其应用于点 p 时，返回 r1 应用于 p 与 r2 应用于 p 的合取。”更抽象地说：“点 p 位于 r1 与 r2 的交集中，当且仅当它同时位于两者之中。”which can be read: “the intersection of r1 and r2 is a region which, when applied to a point p, returns the conjunction of r1 applied to p and r2 applied to p.” Or more abstractly: “a point p lies in the intersection of r1 and r2 if it lies in both r1 and r2.”

The key point is that one can reason directly within the domain semantics, rather than within the semantics of the programming language. = r1 p && (r2 p && r3 p)        (结合律： &&)

5　DSEL 的高级支持5 Advanced Support For DSEL’s

本节介绍一些较新的研究与开发工作，它们有望使 DSL／DSEL 方法对工业级软件开发更具吸引力。In this section I will describe some recent research and development efforts that promise to make the DSL/DSEL methodology even more attractive for industrial-strength software development.

5.1　模块化解释器5.1 Modular Interpreters

Haskell 中的 DSEL 可以看作一种高阶代数结构，一个具有语法“外观与使用方式”的一等值。某种意义上，它只是一种记法，其语义由解释器捕获。这又提供了模块化设计的机会，从而促进系统演进，因为领域语义的变化在许多情况下不可避免。A DSEL in Haskell can be thought of as a higher-order algebraic structure, a first-class value that has the “look and feel” of syntax. In some sense it is just a notation; its semantics is captured by an interpreter. This permits another opportunity for modular design, in turn facilitating evolution of the system since changes in the domain semantics are in many cases inevitable.

多年来，真正模块化的解释器设计一直是编程语言界难以实现的目标。人们尤其希望将不同语言特性分离，以“搭积木”的方式分别赋予解释，再组装这些积木，得到只包含少数、大部分，甚至全部独立语言特性的语言。多位研究者的进展 [Mog89, Ste94, Esp95, LHJ95, LH96, Lia96]，形成了构建这类模块化解释器与编译器的若干关键原则。其中，使用单子 [PJW93, Wad90] 来组织设计，起了关键作用。The design of truly modular interpreters has been an elusive goal in the programming language community for many years. In particular, one would like to design the interpreter so that different language features can be isolated and given individualized interpretations in a “building block” manner. These building blocks can then be assembled to yield languages that have only a few, a majority, or even all of the individual language features. Progress by several researchers [Mog89, Ste94, Esp95, LHJ95, LH96, Lia96] has led to some key principles on which one can base such modular interpreters and compilers. The use of monads [PJW93, Wad90] to structure the design was critical.

这种方法意味着，即使最初设计已经完成很久，仍可加入语言特性，即便它们会根本改变解释器功能。例如，可以构建一系列语言与解释器：先是小型计算器语言，只有数字；然后是带变量的简单一阶语言；再是具有多种调用约定的高阶语言；接着是带错误与异常的语言，等等，如图 5 所示。在每一层，都能加入新的语言特性及其语义，而无须修改任何已有代码。This approach means that language features can be added long after the initial design, even if they involve fundamental changes in the interpreter functionality. For example, one can build a series of languages and interpreters that begin with a small calculator language (just numbers), then a simple first-order language with variables, then a higher-order language with several calling conventions, then a language with errors and exceptions, and so on, as suggested in Figure 5. At each level the new language features can be added, along with their semantics, without altering any previous code.

这种方法不仅可以捕获领域特定语义，还可以捕获领域特定优化。优化可以增量完成，并且彼此独立，也独立于核心语义。这一思想已用于实现传统编译器优化 [LH96, Lia96]，同样的技术也可用于领域特定优化。It is also possible with this approach to capture not only domain-specific semantics, but also domain-specific optimizations. These optimizations can be done incrementally and independently from each other and from the core semantics. This idea has been used to implement traditional compiler optimizations [LH96, Lia96], but the same techniques could be used for domain-specific optimizations.

传统解释器把项、环境和存储等映射为一个答案。相反，模块化单子解释器将项映射为计算，而环境、存储等细节“隐藏”在计算之中。具体地说：A conventional interpreter maps, say, a term, environment, and store, to an answer. In contrast, a modular monadic interpreter maps terms to computations, where the details of the environment, store, etc. are “hidden” in the computation. Specifically:

interp :: Term -> InterpM Value

其中，InterpM Value 是产生最终答案的解释器单子。where InterpM Value is the interpreter monad of final answers.

解释器之所以具有模块化，是因为上述三个部分——项类型、值类型和单子——都可以配置。例如，最初若想为一个小型数值表达式语言构建解释器，可以填写如下定义：What makes the interpreter modular is that all three components above—the term type, the value type, and the monad—are configurable. To illustrate, if we initially wish to have an interpreter for a small number-expression language, we can fill in the definitions as follows:

type Value   = OR Int Bottom
type Term    = TermA
type InterpM = ErrorT Id

第一行将答案域声明为整数与“底”（未定义值）的并集。第二行将项定义为算术运算的抽象语法 TermA。最后一行将解释器单子定义为对恒等单子 Id 的变换。单子变换器 ErrorT 负责错误的可能性，此处即算术异常。此时，解释器的行为就像一个计算器：The first line declares the answer domain to be the union of integers and “bottom” (the undefined value). The second line defines terms as TermA, the abstract syntax for arithmetic operations. The final line defines the interpreter monad as a transformation of the identify monad Id. The monad transformer ErrorT accounts for the possibility of errors; in this case, arithmetic exceptions. At this point the interpreter behaves like a calculator:

Run> ((1+4)*8)
     40
Run> (3/0)
     错误：除以 0
Run> ((1+4)*8)
     40
Run> (3/0)
     ERROR: divide by 0

如果现在希望加入函数调用，可以用函数类型扩展值域，为项类型加入函数调用的抽象语法，再应用单子变换器 EnvT Env，引入环境 Env。Now if we wish to add function calls, we can extend the value domain with function types, add the abstract syntax for function calls to the term type, and apply the monad transformer EnvT Env to introduce an environment Env.

type Value   = OR Int (OR Function Bottom)
type Term    = OR TermF TermA
type InterpM = EnvT Env (ErrorT Id)

下面是一次试运行：Here is a test run:

Run> ((\x.(x+4)) 7)
     11
Run> (x+4)
     错误：未绑定的变量 x
Run> ((\x.(x+4)) 7)
     11
Run> (x+4)
     ERROR: unbound variable: x

还可以进一步向解释器加入条件表达式、惰性求值、letrec 声明、非确定性、续延、跟踪、性能分析，乃至引用和赋值等特性。每当需要新的值域（例如布尔值）时，就扩展 Value 类型；要加入新的语义特性（例如存储或续延），则应用相应的单子变换器。We can further add other features such as conditionals, lazy evaluation, letrec declarations, nondeterminism, continuations, tracing, profiling, and even references and assignment, to our interpreter. Whenever a new value domain (such as Boolean) is needed, we extend the Value type; and to add a new semantic feature (such as a store or continuation), we apply the corresponding monad transformer.

5.2　语言工具与插桩5.2 Language Tools and Instrumentation

尽管调试器、性能分析器、跟踪器和性能监控器等语言工具对软件开发十分重要，传统上，人们处理它们的方式却相当零散。我认为，更有章法地设计这类工具，会有益于软件开发过程。事实上，可以建立一种工具生成方法，具备前面提出的许多目标：高度模块化、面向特定领域，并且能够演进。在这一方案中，工具可以逐层叠加而互不影响，因此修改和增补都很容易。在框架中指定的工具，可以自动与相应的标准语义组合，产生同时包含两者行为的复合语义。图 6 是整个方法的流程图，图 7 展示其可组合性。Despite the importance in software development of language tools such as debuggers, profilers, tracers, and performance monitors, traditionally they have been treated in rather ad hoc ways. I believe that a more disciplined approach to designing such tools will benefit the software development process. Indeed, it is possible to develop a methodology for tool generation that shares much with previously identified goals: it is highly-modular, domain-specific, and evolvable. Under this scheme, tools can be layered onto the system without affecting each other; changes and additions are thus easily accomplished. 6　结论6 Conclusion

本文介绍了一种设计与实现领域特定语言的方法。其中一些技术广为人知，与实现传统编程语言的技术相似；另一些新得多，但许多技术已经得到足够充分的应用，让我们对它们的成功抱有信心。嵌入式 DSL 的概念尤其有吸引力，因为它既简单，又强大。I have described a methodology for designing and implementing domain-specific languages. Some of the techniques to do this are well-known, being similar to techniques for implementing conventional programming languages. Others are much newer, yet many of these have been used well enough to give us confidence of their success. The notion of an embedded DSL is especially attractive, due to its simplicity and power.

我鼓励读者寻找使用 DSL 的机会，并在需要时创建新的 DSL，无论多么小巧。设计良好的 DSL 应当捕获应用领域的本质；从这一意义上说，没有比这更好的软件系统组织方式。DSL 设计没有严格固定的规则，但以下准则或许有用：I urge the reader to search for opportunities to use DSL’s and to create new ones—however small—when the need arises. A well-designed DSL should capture the essence of one’s application domain, and in that sense there is no better way to structure one’s software system. There are no hard-fast rules for designing a DSL, but the following guidelines may be useful:

  1. 1. 遵循 KISS 原则：保持简单，别把事情弄复杂。1. Use the KISS (keep it simple, stupid) principle.
  2. 2. “小语言”是好东西；读一读 Jon Bentley 的文章。2. “Little languages” are a Good Thing; read Jon Bentley’s article.
  3. 3. 聚焦领域语义，不要纠缠于语法。3. Concentrate on the domain semantics; do not get hung up on syntax.
  4. 4. 不要让性能支配设计，也不要让设计压倒性能。4. Don’t let performance dominate the design; and don’t let the design dominate performance.
  5. 5. 为设计建立原型，细化并迭代。5. Prototype your design; refine and iterate.
  6. 6. 心中始终想着最终用户；记住：成功＝满意的客户。6. Keep the end user in mind; remember that Success = A Happy Customer.
