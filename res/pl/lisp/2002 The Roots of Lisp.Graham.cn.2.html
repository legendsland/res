Lisp 的根源

The Roots of Lisp

保罗·格雷厄姆

paul graham

草稿，2002 年 1 月 18 日。

Draft, January 18, 2002.

1960 年，John McCarthy 发表了一篇非凡的论文。他为编程所做的事，有点像欧几里得为几何学所做的事。¹ 他展示了如何仅凭少数几个简单运算符和一种表示函数的记法，构建出一整门编程语言。他把这门语言称为 Lisp，即“List Processing”（表处理），因为他的一个核心思想，就是用一种称为列表的简单数据结构，同时表示代码和数据。

In 1960, John McCarthy published a remarkable paper in which he did for programming something like what Euclid did for geometry.1 He showed how, given a handful of simple operators and a notation for functions, you can build a whole programming language. He called this language Lisp, for “List Processing,” because one of his key ideas was to use a simple data structure called a list for both code and data.

理解 McCarthy 的发现很有价值，不仅因为它是计算机历史上的里程碑，也因为它为我们这个时代编程的发展方向提供了一个模型。在我看来，迄今真正简洁、一致的编程模型有两个：C 模型和 Lisp 模型。它们就像两处高地，中间则是泥泞的低地。随着计算机能力增强，新开发的语言一直在稳步向 Lisp 模型靠近。过去 20 年里，设计新编程语言的一种流行配方，就是以 C 的计算模型为基础，再逐项加入取自 Lisp 模型的部分，例如运行时类型机制和垃圾回收。

It's worth understanding what McCarthy discovered, not just as a landmark in the history of computers, but as a model for what programming is tending to become in our own time. It seems to me that there have been two really clean, consistent models of programming so far: the C model and the Lisp model. These two seem points of high ground, with swampy lowlands between them. As computers have grown more powerful, the new languages being developed have been moving steadily toward the Lisp model. A popular recipe for new programming languages in the past 20 years has been to take the C model of computing and add to it, piecemeal, parts taken from the Lisp model, like runtime typing and garbage collection.

本文将尝试用尽可能简单的语言，解释 McCarthy 的发现。目的不只是了解某人在四十年前得到的一个有趣理论结果，而是展示语言正在走向何方。Lisp 的不同寻常之处，事实上也是它的决定性特征，是它可以用自身来编写。为了理解 McCarthy 这句话的含义，我们将重走他的探索之路，把他的数学记法翻译成可运行的 Common Lisp 代码。

In this article I'm going to try to explain in the simplest possible terms what McCarthy discovered. The point is not just to learn about an interesting theoretical result someone figured out forty years ago, but to show where languages are heading. The unusual thing about Lisp, in fact, the defining quality of Lisp, is that it can be written in itself. To understand what McCarthy meant by this, we're going to retrace his steps, with his mathematical notation translated into running Common Lisp code.

在算术中，表达式 1 + 1 的值是 2。有效的 Lisp 表达式也有值。如果表达式 e 产生一个值 v，我们就说 e 返回 v。 接下来，我们要定义有哪些表达式，以及每种表达式返回什么值。如果表达式是一个列表，我们把第一个元素称为运算符，其余元素称为参数。我们将定义七个原始运算符，这里的“原始”是指类似公理的基础地位：quote、atom、eq、car、cdr、cons 和 cond。

In arithmetic the expression 1 + 1 has the value 2. Valid Lisp expressions also have values. If an expression e yields a value v we say that e returns v. Our next step is to define what kinds of expressions there can be, and what value each kind returns. If an expression is a list, we call the first element the operator and the remaining elements the arguments. We are going to define seven primitive (in the sense of axioms) operators: quote, atom, eq, car, cdr, cons, and cond.

  1. (quote x) 返回 x。为便于阅读，我们把 (quote x) 简写为 'x。

> (atom '())

    > (atom (atom 'a))

    引用可能显得有些陌生，因为其他语言很少有类似的东西。它与 Lisp 最鲜明的特征之一紧密相连：代码和数据由相同的数据结构构成，而 quote 运算符就是区分二者的方式。

  3. 如果 x 和 y 的值是同一个原子，或者二者都是空表，(eq x y) 返回 t；否则返回 ()。

    > (cdr '(a b c))

    (cons x y) expects the value of y to be a list and returns a list containing the value of x followed by the elements of the value of y.

    > (cons 'a '(b c))
(a b c)
> (cons 'a (cons 'b (cons 'c '())))
(a b c)
> (car (cons 'a '(b c)))

> (cdr (cons 'a '(b c)))
(b c)

  7. (cond (p1 e1) … (pn en)) 按如下方式求值：依次对各个 p 表达式求值，直到某个表达式返回 t。找到后，就返回相应 e 表达式的值，作为整个 cond 表达式的值。

    (cond (p1 e1) … (pn en)) is evaluated as follows. The p expressions are evaluated in order until one returns t. When one is found, the value of the corresponding e expression is returned as the value of the whole cond expression.

    > (cond ((eq 'a 'b) 'first)

In five of our seven primitive operators, the arguments are always evaluated when an expression beginning with that operator is evaluated.2 We will call an operator of that type a function.

4 The Surprise

到这里，我们已经能定义连接列表、把一个表达式替换为另一个表达式等函数。记法也许很优美，但那又怎样？现在惊喜来了。事实证明，我们还能写出一个充当这门语言解释器的函数：它接收任意 Lisp 表达式作为参数，并返回该表达式的值。代码如下：

So we can define functions that concatenate lists, substitute one expression for another, etc. An elegant notation, perhaps, but so what? Now comes the surprise. We can also, it turns out, write a function that acts as an interpreter for our language: a function that takes as an argument any Lisp expression, and returns its value. Here it is:

(defun eval. (e a)
  (cond
    ((atom e) (assoc. e a))
    ((atom (car e))
     (cond
       ((eq (car e) 'quote) (cadr e))
       ((eq (car e) 'atom) (atom    (eval. (cadr e) a)))
       ((eq (car e) 'eq)    (eq     (eval. (cadr e) a)
                                    (eval. (caddr e) a)))
       ((eq (car e) 'car)   (car    (eval. (cadr e) a)))
       ((eq (car e) 'cdr)   (cdr    (eval. (cadr e) a)))
       ((eq (car e) 'cons) (cons    (eval. (cadr e) a)
                                    (eval. (caddr e) a)))
       ((eq (car e) 'cond) (evcon. (cdr e) a))
       ('t (eval. (cons (assoc. (car e) a)
                        (cdr e))
                  a))))
    ((eq (caar e) 'label)
     (eval. (cons (caddar e) (cdr e))
            (cons (list (cadar e) (car e)) a)))
    ((eq (caar e) 'lambda)
     (eval. (caddar e)
            (append. (pair. (cadar e) (evlis. (cdr e) a))
                     a)))))

(defun evcon. (c a)
  (cond ((eval. (caar c) a)
         (eval. (cadar c) a))
        ('t (evcon. (cdr c) a))))

(defun evlis. (m a)
  (cond ((null. m) '())
        ('t (cons (eval. (car m) a)
                  (evlis. (cdr m) a)))))

eval. 的定义比前面见过的任何定义都长。下面看看各个部分是如何工作的。

The definition of eval. is longer than any of the others we'five seen before. Let's consider how each part works.

这个函数接收两个参数：e 是待求值的表达式；a 是一个列表，表示各个原子作为函数调用中的形参而获得的值。这个列表称为环境，其形式与 pair. 创建的列表相同。我们编写 pair. 和 assoc.，正是为了构建和搜索这些列表。

The function takes two arguments: e, the expression to be evaluated, and a, a list representing the values that atoms have been given by appearing as parameters in function calls. This list is called the environment, and it is of the form created by pair.. It was in order to build and search these lists that we wrote pair. and assoc..

eval. 的主干是一个包含四个子句的 cond 表达式。如何对表达式求值，取决于它的类型。第一个子句处理原子。如果 e 是原子，就在环境中查找它的值：

The spine of eval. is a cond expression with four clauses. How we evaluate an expression depends on what kind it is. The first clause handles atoms. If e is an atom, we look up its value in the environment:

> (eval. 'x '((x a) (y b)))
a

eval. 的第二个子句又是一个 cond，用于处理形如 (a …) 的表达式，其中 a 是原子。这包括原始运算符的所有用法，每个运算符都有对应的子句。

The second clause of eval. is another cond for handling expressions of the form (a …), where a is an atom. These include all the uses of the primitive operators, and there is a clause for each one.

> (eval. '(eq 'a 'a) '())
t
> (eval. '(cons x '(b c))
         '((x a) (y b)))
(a b c)

除 quote 外，这些子句都会调用 eval. 来求出参数的值。

All of these (except quote) call eval. to find the value of the arguments.

最后两个子句更复杂一些。对 cond 表达式求值时，我们调用辅助函数 evcon.，它递归地逐个检查子句，寻找第一个元素返回 t 的子句。找到后，就返回该子句第二个元素的值。

The last two clauses are more complicated. To evaluate a cond expression we call a subsidiary function called evcon., which works its way through the clauses recursively, looking for one in which the first element returns t. When it finds such a clause it returns the value of the second element.

> (eval. '(cond ((atom x) 'atom)
                ('t 'list))
         '((x '(a b))))
list

它最终返回 a。

which eventually returns a.

最后，对形如 ((lambda (p1 … pn) e) a1 … an) 的表达式求值时，先调用 evlis.，得到各个实参 a1 … an 的值所组成的列表 (v1 … vn)，再把 (p1 v1) … (pn vn) 加到环境前端，然后对 e 求值。因此：

Finally, an expression of the form ((lambda (p1 … pn) e) a1 … an) is evaluated by first calling evlis. to get a list of values (v1 … vn) of the arguments a1 … an, and then evaluating e with (p1 v1) … (pn vn) appended to the front of the environment. So

(eval. '((lambda (x y) (cons x (cdr y)))
         'a
         '(b c d))
       '())

会变成：

becomes

(eval. '(cons x (cdr y))
       '((x a) (y (b c d))))

它最终返回 (a c d)。

which eventually returns (a c d).

5 后续影响

5 Aftermath

现在已经理解 eval 如何工作，让我们退后一步，想想这意味着什么。我们得到的是一个极其优美的计算模型。只用 quote、atom、eq、car、cdr、cons 和 cond，就能定义一个真正实现了这门语言的函数 eval.；再利用它，就能定义任何我们想要的其他函数。

Now that we understand how eval works, let's step back and consider what it means. What we have here is a remarkably elegant model of computation. Using just quote, atom, eq, car, cdr, cons, and cond, we can define a function, eval., that actually implements our language, and then using that we can define any additional function we want.

当然，计算模型早已存在，其中最著名的是图灵机。但阅读图灵机程序并不怎么让人获得启发。如果想要一种描述算法的语言，你可能会希望它更抽象一些，而这正是 McCarthy 定义 Lisp 的目标之一。

There were already models of computation, of course, most notably the Turing Machine. But Turing Machine programs are not very edifying to read. If you want a language for describing algorithms, you might want something more abstract, and that was one of McCarthy's aims in defining Lisp.

他在 1960 年定义的语言还缺少很多东西：没有副作用，没有顺序执行，反正顺序执行也只有与副作用结合时才有用；没有实用的数字，⁴ 而且采用动态作用域。但只需增加少得令人惊讶的代码，就能弥补这些局限。Steele 和 Sussman 在一篇著名论文《解释器的艺术》中展示了如何做到这一点。⁵

The language he defined in 1960 was missing a lot. It has no side-effects, no sequential execution (which is useful only with side effects anyway), no practical numbers,4 and dynamic scope. But these limitations can be remedied with surprisingly little additional code. Steele and Sussman show how to do it in a famous paper called "The Art of the Interpreter."5

如果你理解 McCarthy 的 eval，理解的就不仅仅是语言史上的某个阶段。这些思想至今仍是 Lisp 的语义核心。因此，从某种意义上说，研究 McCarthy 的原始论文，就是在了解 Lisp 究竟是什么。与其说 Lisp 是 McCarthy 设计出来的，不如说是他发现的。它本质上并不是专门用于人工智能、快速原型开发，或其他类似层次任务的语言。它是你尝试将计算公理化时得到的东西，或者说，得到的东西之一。

If you understand McCarthy's eval, you understand more than just a stage in the history of languages. These ideas are still the semantic core of Lisp today. So studying McCarthy's original paper shows us, in a sense, what Lisp really is. It's not something that McCarthy designed so much as something he discovered. It's not intrinsically a language for AI or for rapid prototyping, or any other task at that level. It's what you get (or one thing you get) when you try to axiomatize computation.

随着时间推移，“中位数语言”，也就是处于中位数位置的程序员所使用的语言，一直在不断向 Lisp 靠近。因此，理解 eval，也就是理解一种很可能在未来很长时间内占据主导地位的计算模型。

Over time, the median language, meaning the language used by the median programmer, has grown consistently closer to Lisp. So by understanding eval you're understanding what will probably be the main model of computation well into the future.

说明

Notes

在把 McCarthy 的记法翻译成可运行代码时，我尽量少作改动。我曾想让代码更容易阅读，但还是希望保留原作的风味。

In translating McCarthy's notation into running code I tried to change as little as possible. I was tempted to make the code easier to read, but I wanted to keep the flavor of the original.

在 McCarthy 的论文中，假用 f 表示，而不是空表。我用 () 表示假，是为了让示例能在 Common Lisp 中运行。代码没有任何地方依赖“假恰好也是空表”这一点；谓词返回的结果从来不会被拿来作为 cons 的列表尾部。

In McCarthy's paper, falsity is represented by f, not the empty list. I used () to represent falsity so that the examples would work in Common Lisp. The code nowhere depends on falsity happening also to be the empty list nothing is ever consed onto the result returned by a predicate.

我略去了如何用点对构建列表，因为理解 eval 并不需要它。我也没有提到 apply，虽然 McCarthy 在 1960 年称为通用函数的其实是 apply，那是它的一个很早的版本，主要用途是给参数加引用；当时 eval 只是 apply 调用的一个子程序，负责完成全部实际工作。

I skipped building lists out of dotted pairs, because you don't need them to understand eval. I also skipped mentioning apply, though it was apply (a very early form of it, whose main purpose was to quote arguments) that McCarthy called the universal function in 1960 eval was then just a subroutine that apply called to do all the work.

我把 list 和各个 cxr 定义为缩写，因为 McCarthy 就是这样做的。实际上，所有 cxr 都可以定义为普通函数。list 也一样，只要稍微修改 eval，让函数可以接收任意数量的参数即可，而这很容易做到。

I defined list and the cxrs as abbreviations because that's how McCarthy did it. In fact the cxrs could all have been defined as ordinary functions. So could list if we modified eval, as we easily could, to let functions take any number of arguments.

McCarthy 的论文只列出了五个原始运算符。他使用了 cond 和 quote，但可能把它们看作元语言的一部分。同样，他也没有定义逻辑运算符 and 和 not，不过这不是什么大问题，因为可以把足够好用的版本定义为函数。

McCarthy's paper only had five primitive operators. He used cond and quote but may have thought of them as part of his metalanguage. He likewise didn't define the logical operators and and not, but this is less of a problem because adequate versions can be defined as functions.

在 eval. 的定义中，我们调用了 pair. 和 assoc. 等其他函数。但凡是用原始运算符定义的函数，其调用都可以替换成对 eval. 的调用。也就是说：

In the definition of eval. we called other functions like pair. and assoc., but any call to one of the functions we defined in terms of the primitive operators could be replaced by a call to eval.. That is,

(assoc. (car e) a)

可以写成：

could have been written as

(eval. '((label assoc.
                (lambda (x y)
                  (cond ((eq (caar y) x) (cadar y))
                        ('t (assoc. x (cdr y))))))
         (car e)
         a)
        (cons (list 'e e) (cons (list 'a a) a)))

McCarthy 的 eval 有一个小错误。第 16 行写的内容相当于 (evlis. (cdr e) a)，而不是仅仅 (cdr e)，导致调用具名函数时，参数被求值了两次。这表明，在论文提交时，这个版本的 eval 很可能还没有用 IBM 704 机器语言实现。这也说明，不实际运行程序，就很难确信任何具有一定长度的程序是正确的。

There was a small bug in McCarthy's eval. Line 16 was (equivalent to) (evlis. (cdr e) a) instead of just (cdr e), which caused the arguments in a call to a named function to be evaluated twice. This suggests that this description of eval had not yet been implemented in IBM 704 machine language when the paper was submitted. It also shows how hard it is to be sure of the correctness of any length of program without trying to run it.

我还在 McCarthy 的代码中遇到了另一个问题。在给出 eval 的定义之后，他又举了一些高阶函数的例子，也就是以其他函数作为参数的函数。他定义了 maplist：

I encountered one other problem in McCarthy's code. After giving the definition of eval he goes on to give some examples of higher-order functions, functions that take other functions as arguments. He defines maplist:

(label maplist
       (lambda (x f)
         (cond ((null x) '())
               ('t (cons (f x) (maplist (cdr x) f))))))

然后用它编写了一个进行符号求导的简单函数 diff。但 diff 传给 maplist 的函数把 x 用作形参，而对 x 的引用被 maplist 内部的形参 x 捕获了。⁶

then uses it to write a simple function diff for symbolic differentiation. But diff passes maplist a function that uses x as a parameter, and the reference to it is captured by the parameter x within maplist.6

连高阶 Lisp 函数的第一个示例，都因为动态作用域而出错，这充分说明了动态作用域的危险。McCarthy 在 1960 年可能还没有完全意识到动态作用域的影响。动态作用域在 Lisp 实现中保留了令人惊讶的漫长时间，直到 Sussman 和 Steele 于 1975 年开发出 Scheme。词法作用域并不会让 eval 的定义复杂多少，但可能会增加编译器的编写难度。

It's an eloquent testimony to the dangers of dynamic scope that even the very first example of higher-order Lisp functions was broken because of it. It may be that McCarthy was not fully aware of the implications of dynamic scope in 1960. Dynamic scope remained in Lisp implementations for a surprisingly long time, until Sussman and Steele developed Scheme in 1975. Lexical scope does not complicate the definition of eval very much, but it may make compilers harder to write.
