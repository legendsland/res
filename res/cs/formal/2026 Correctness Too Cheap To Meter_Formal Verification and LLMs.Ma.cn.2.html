这里的想法是，你要证明坏事永远不会发生，因此必须保证正确的事情始终发生。例如，TLA+ 的第 17 行有一个“无死锁”不变量，要求 next 始终处于可执行状态。而 next 这个动作规定，系统必须始终能够执行加锁或解锁中的某一个。The idea is that you want to prove that nothing bad ever happens. 这意味着，我们始终能够迈出下一步，因此不会陷入死锁。另一个我想强调的地方，可能与你以往听说的 TLA+ 有所不同：我们的研究关注非常底层、细粒度的规约，而不是大型、高层次的协议级规约。因为要发现真实的实现缺陷，恰恰需要底层规约。So, this means that we can always take a next step, and therefore that we've never deadlocked. And so, another thing that I'd like to highlight, it might be different if you've ever heard of TLA+ before, is that in our work we want to focus on really low level fine grained specifications. 所以，这次演讲展示的 TLA+ 会比通常的例子细致得多。有了 TLA+ 规约之后，还需要把它交给模型检查器，才能真正发挥作用。TLA+ 生态中的模型检查器叫作 TLC。你可以把 TLA+ 规约看作是在定义一个状态空间及其中的迁移，有点像有限状态机。So, this explains why our TLA+ that I'll be showing in this talk is quite a bit more fine grained than usual. Now, once you have a spec in TLA+, we need to pass it to a model checker to get any use out of it. So, the model checker in TLA+ ecosystem is called TLC. So, you can think of your TLA+ spec as defining a state space and its transitions, like a bit like a finite state machine.

TLC 会穷尽探索状态空间中的所有路径。以我们的规约为例，锁要么处于空闲状态，要么处于持有状态。规约定义了两种迁移：要么解锁，要么解锁——原转录在这里把两种操作都说成了解锁。这就是两个状态迁移。TLC 会检查这些路径，并在每一步检查所有不变量。And TLC is a tool that exhaustively explores all the paths within the state space. So, in our spec for example, we have the lock either idle or held. And so, the spec has defined two transitions, either you unlock the lock or you unlock it. And so, these are two state transitions. TLC will then check each of these paths. Uh at each step, TLC will check each of the invariants.

因此，一旦发现违反不变量，要么是系统有缺陷，要么是规约有缺陷。这里，在第三行的第一个 init 动作中初始化状态时，我们把 ack 设为了 false。然而，第八行的 unlock 动作又要求 ack 已经成立。And so, any of these violations will either mean a bug or a bug in the spec. 所以，当 TLC 检查这个状态空间、检查这份规约时，就会发现“无死锁”不变量被违反了。因为进入 held 状态之后，我们再也无法确认 ack，也就再也无法解锁。TLC 会显示这个不变量检查失败。它非常有助于精确定位这类问题。And so, when TLC goes to check our state space, check our spec, we'll find that the no deadlock invariant is violated because when we go into the held state, we're never able to ack and we're never able to unlock again. 轨迹验证：规约与代码的解锁行为Trace Validation: Unlocking Specs vs. Code

如果规约有问题，比如大语言模型加入了某些我们没有预期的内容，TLC 就能帮助发现它。轨迹验证是 TLC 提供的另一种机制，它会检查：能否在实现的执行日志，也就是真实执行，与抽象 TLA+ 规约中的动作之间，找到一个映射。这用来确保规约与实现相符。开展轨迹验证时，我们首先从系统获取执行日志。So, if there's a problem within your spec, for example, an LLM has inserted something that we don't expect, TLC will help you find it. Trace validation is another mechanism provided by TLC that checks if we can find a mapping between traced implementation logs, so real executions, and the actions in our abstract TLA+ spec. This ensures that the spec conforms with the implementation. We perform trace validation by getting execution logs from the system.

中间展示的是这份锁操作日志。按照原转录的说法，它显示我们可以先解锁，再解锁，然后又加上锁。接着，我们把这些记录与实现及规约状态空间中的路径进行匹配。前面展示的规约例子无法再次解锁，但这条执行轨迹却能够解锁，然后重新加锁。So, in the middle here we have this lock log. It shows that we can unlock, then we can unlock, and we've locked again. And then we match these against paths in the implementation and the spec state space. So, as you can see, the spec example I've shown before, we're not able to unlock again. And yet, in this execution trace we're able to unlock and then lock again.

这说明规约与代码不一致。通常，这意味着规约限制得过严，或者遗漏了某些内容。比如，在实际实现，也就是 Python 服务器里，也许确实存在一个 ack 动作，只是我们忘了在 TLA+ 中对它建模。轨迹验证可以帮助凸显规约与代码之间的这些差异。So, this means that our spec doesn't match our code. And usually this means that the spec is either too restrictive or it maybe is missing something. So, maybe in our implementation, the Python server, we actually do have an ack action, but we've just forgotten to model it in the TLA+. So, trace validation can help highlight these discrepancies between the specs and the code.

轨迹验证不仅需要一份 TLA+ 形式化规约，还需要在代码中插桩，并用 TLA+ 编写两者之间的映射。这确实需要一定的人工投入，后面我们会继续讨论。另一个重要之处在于，轨迹验证也能限制幻觉的影响，因为我们始终可以核对，规约是否与代码的行为相符。接下来看看典型的 TLA+ 开发工作流。Trace validation requires not only having a formal spec in the TLA+, but also instrumentation in your code, and also writing a TLA+ mapping between the two. And this does take some human effort to write, and we'll talk about more of this later. Trace validation is also importantly another aspect that limits the impact of hallucinations, since we can always confirm that the spec matches the behavior of the code. So, this is a typical TLA+ developer workflow.

开发者为一个新系统建模时，通常先探索代码库：阅读文档、了解有哪些模块，并思考希望检查哪些不变量。接着，他们一般会起草 TLA+ 规约，再进行模型检查和轨迹验证，以确保其符合规约要求，并且内部自洽。So, when a developer goes to model a new system, they usually start by exploring the code base. So, for example, reading the docs, understanding what modules there are, and figuring out what invariants they might want to check. Next, they'll typically draft a TLA+ specification, and then move on to model checking and trace validating it to ensure that it conforms with the spec and is internally consistent.

更棘手的是，一般情况下，并没有什么办法能真正自动化这些繁琐工作，尤其是在我们所关心的生产系统规模上。不过，现在是 2026 年，对于一切“做 X 太费工夫”的问题，如今的答案似乎都是：扔给大语言模型。在大多数情况下，我们自然会担心幻觉之类的问题。The kicker here is that nothing can really automate this toil in general, especially not at the scale of the production systems that we're interested in.
